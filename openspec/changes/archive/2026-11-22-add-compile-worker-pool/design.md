## Decisions
CompilePool owns fixed named std threads and a bounded sync_channel. Nonblocking try_send returns Busy on saturation. The receiver mutex covers only dequeue, never compilation. A shared immutable CubeService supplies exact version selection. Owned Query/CompileContext cross the thread boundary unchanged. CompileTask awaits a Tokio oneshot receiver; oneshot send needs no runtime. Dropping a result handle never prevents worker reuse. Panic unwinding drops that job's sender, produces Unavailable, and is contained before the next job. Abort builds cannot contain panics.

Drop closes admission and detaches workers, which drain accepted jobs and exit; it never joins on an async runtime. Explicit shutdown consumes the pool and joins workers; call it outside async runtime threads. It waits for accepted jobs and cannot forcibly stop a hung planner. Startup failure closes admission for already-started workers. Zero worker/queue counts are invalid. Model versions are registered before constructing the shared service. Busy is admission failure, not a compile result. Validation/metadata stay on the existing core API.

Alternatives: spawn_blocking uses a shared runtime pool, not a fixed compilation budget; unbounded channels allow unchecked queue growth; coupling gRPC now would mix protocol and scheduling. Public tests compare complete real compilation outputs, errors, versions and restrictive contexts from a current-thread runtime. Internal deterministic barriers test worker identities, concurrent capacity, saturation, dropped results and panic recovery. No timing sleeps or SQL execution.

Sources: https://doc.rust-lang.org/std/sync/mpsc/struct.SyncSender.html#method.try_send ; Tokio 1.52.1 local sync/oneshot source documents synchronous send and asynchronous receive. Final delivery requires CI, local real Docker smoke and different-vendor review.
